# 構成案の作り方

構成案は人が承認する。承認者が「どのアカウントに、何を作り、いくらかかり、どう消すか」を1画面で判断できるように書く。書式は `templates/plan.md`。

## 良い題材の条件

すべて満たすものを選ぶ。満たせない場合は、構成案の「リスク」に理由と代替案を書く。

1. **結果がCLIで確かめられる**: 各手順の確認ポイントを、コマンドの出力で判定できる。
2. **費用が上限内**: 見積もりが $0.80(上限 $1.00 の8割)以下。`cost-guardrails` を参照。
3. **待ち時間が短い**: 作成・削除に10分以上かかるリソース(CloudFront ディストリビューション、RDS、OpenSearch、NAT Gateway を含む VPC など)を避ける。使う場合は所要時間に含める。
4. **外部に依存しない**: ドメイン取得、メールの受信確認(SES サンドボックスの検証など)、外部SaaSのアカウントが要らない。
5. **指定リージョンで一般提供**: プレビュー機能や未提供リージョンの機能を使わない。
6. **消し切れる**: 作ったものが `handson-job-id` タグか IaC の destroy で全部消える。消せない・消すのに日数がかかるもの(KMS キーの削除待機など)は避ける。
7. **1本で1つのことを学ぶ**: 対象サービスの中心的な使い方を1つ選ぶ。関連サービスは、中心の動作を確かめるのに必要な分だけ。

## レベル別の章立て例

### 入門(60分)

| 章 | 目安 | 内容 |
| --- | --- | --- |
| 事前準備 | 10分 | 環境変数、IaC の準備、アカウント確認 |
| 基本リソースを作る | 15分 | IaC で中心となるリソースを作る |
| 基本操作を試す | 20分 | CLI で中心となる操作を2〜3種類行い、結果を確認する |
| 設定を変えて違いを見る | 10分 | 1つの設定を変え、動作の違いを確認する |
| 後片付け | 5分 | destroy とタグ検索による確認 |

例(Amazon SQS 入門): 標準キューを作る → メッセージを送信・受信・削除する → 可視性タイムアウトを変えて再受信の挙動を見る → 後片付け。

### 応用(120分)

| 章 | 目安 | 内容 |
| --- | --- | --- |
| 事前準備 | 10分 | 同上 |
| 構成を作る | 20分 | 中心のサービスと連携先(Lambda など)を IaC で作る |
| 連携を動かす | 30分 | イベントを流し、連携先での処理をログで確認する |
| 異常系を試す | 30分 | 失敗させて、リトライ・DLQ・アラームなどの動きを確認する |
| 運用の観点 | 20分 | メトリクス、権限の絞り込み、設定の見直し |
| 後片付け | 10分 | 同上(自動作成されるリソースの確認を含む) |

例(Amazon SQS 応用): SQS → Lambda のイベントソースマッピング → 処理失敗時の DLQ への移動 → CloudWatch メトリクスで滞留を確認 → 後片付け。

## 手順の作り方

- 章立ては「作る → 使う → 確かめる → 消す」の順にする。
- 各手順に確認ポイントの概要(何を見れば成功とわかるか)を付ける。詳細は執筆担当が書く。
- コンソール操作が必要な手順には「コンソール手順(検証はCLI代替)」と印を付ける。
- 時間課金のリソースがある場合は、作成から削除までを所要時間の範囲に収め、実行時間の上限(60分)を超えないようにする。
